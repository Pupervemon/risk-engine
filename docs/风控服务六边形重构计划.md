# 风控服务六边形架构重构方案

版本：`2026-05-08`

状态：`draft`

本文规划 `risk-server` 从当前 `service + transport` 结构迁移到六边形架构的实施路线。目标是先完成架构边界重构，保持外部接口、Redis key、配置格式和运行行为稳定；统计增强、规则引擎化、存储替换等能力放到后续阶段。

## 1. 背景与目标

当前仓库是一个 Go 单仓双服务：

- `cmd/captcha-server`
- `cmd/risk-server`

其中 `captcha` 服务已经按六边形架构拆分为 `domain`、`application`、`application/ports`、`adapter`、`bootstrap`。`risk` 服务仍主要集中在：

- `internal/risk/service/risk.go`
- `internal/risk/service/ip_admin.go`
- `internal/risk/transport/*`

当前 `RiskService` 同时承担以下职责：

- 实现 `risk-proto` 生成的 gRPC server 接口。
- 编排风控检测、事件上报、黑名单写入、用户限流。
- 直接操作 Redis。
- 持有 Redis Lua 脚本。
- 使用 shared config 结构。
- 记录日志。
- 生成风险 IP 洞察、风险事件、后台查询响应。

这会导致业务规则和基础设施细节耦合较紧。随着后续增加统计、规则配置、更多维度风控、后台运营能力，当前结构会让测试、扩展和回归验证成本持续上升。

本次重构目标：

1. 将风控核心规则从 Redis、gRPC、HTTP、Gin、proto DTO 中解耦。
2. 用 application port 固定入站和出站边界。
3. 保留现有对外 HTTP/gRPC API 行为。
4. 保留现有 Redis key 和 TTL 语义，避免数据迁移。
5. 建立可单测的业务用例层。
6. 让 `cmd/risk-server/main.go` 只负责进程级装配和生命周期。

## 2. 当前结构梳理

### 2.1 服务入口

路径：

```text
cmd/risk-server/main.go
```

当前职责：

- 读取 `configs/risk.*.yaml` 和环境变量。
- 初始化 logger。
- 初始化 Redis client。
- 创建 `riskservice.NewRiskService`。
- 组装 HTTP router。
- 创建 gRPC server，并直接注册 `RiskService`。
- 初始化 Nacos 注册中心。
- 启动 HTTP/gRPC server。
- 处理优雅关闭。

问题：

- 入口直接知道业务 service 的具体构造细节。
- gRPC 注册对象也是业务 service 本身，协议层和应用层没有边界。
- Redis client 被同时传给业务 service 和 HTTP health router，后续扩展多个 Redis client 时会进一步膨胀。

### 2.2 核心业务代码

路径：

```text
internal/risk/service/risk.go
internal/risk/service/ip_admin.go
```

当前能力：

- `Check`
  - 请求空值校验。
  - IP 为空拒绝。
  - IP / 用户黑名单检测。
  - IP 维度限流。
  - 登录场景失败次数检测。
  - 写入风险 IP 洞察。
- `ReportEvent`
  - 当前只支持登录场景。
  - 登录成功清除失败计数。
  - 登录失败累加失败计数。
  - 写入风险 IP 洞察。
- `AddBlacklist`
  - 写入 IP 或用户维度黑名单。
  - 记录黑名单洞察事件。
- `OnlineSelfTest`
  - 用户维度限流。
- `JudgeSubmission`
  - 用户维度限流。
- 风险 IP 后台查询
  - 列表查询。
  - 单 IP 详情。
  - 单 IP 事件历史。
  - 风险等级和 flags 计算。

主要耦合点：

- 业务用例直接 import `github.com/redis/go-redis/v9`。
- 业务用例直接 import `risk-proto` 的 pb 类型。
- 业务用例直接返回 gRPC status error。
- 业务用例直接 import `internal/shared/config`。
- 风险 IP 后台查询 DTO 放在 `service` 包中，HTTP handler 直接引用。
- Redis key、Lua 脚本、风险洞察序列化、分页查询、业务判定逻辑混在同一个包。

### 2.3 HTTP 传输层

路径：

```text
internal/risk/transport
```

当前能力：

- `GET /health`
- `GET /info`
- `GET /api/v1/admin/risk-ips`
- `GET /api/v1/admin/risk-ips/{ip}`
- `GET /api/v1/admin/risk-ips/{ip}/events`
- 管理接口网关 header 鉴权。
- Swagger 注释和文档模型。

主要问题：

- `RiskAdminReader` 接口定义在 transport 包，但参数和返回值直接依赖 `internal/risk/service`。
- 传输层和业务层之间没有 application port，后续迁移 DTO 会牵动 HTTP handler。

## 3. 六边形架构目标形态

目标依赖方向：

```text
cmd/risk-server
  -> internal/risk/bootstrap
  -> internal/risk/application + application/ports
  -> internal/risk/domain

adapter/inbound/http
  -> application/ports
  -> domain

adapter/inbound/grpc
  -> application/ports
  -> domain
  -> risk-proto

application
  -> application/ports
  -> domain

adapter/outbound/redis
  -> application/ports
  -> domain
  -> redis

bootstrap
  -> shared/config
  -> concrete adapters
```

边界原则：

- `domain` 不依赖 Redis、Gin、gRPC、proto、zap、shared config。
- `application` 不依赖 Redis、Gin、gRPC、proto、shared config。
- `adapter/inbound/grpc` 负责 proto DTO 和 application command/result 的转换。
- `adapter/inbound/http` 负责 HTTP 参数解析、鉴权、错误映射、响应输出。
- `adapter/outbound/redis` 负责 Redis key、Lua、序列化、TTL、分页读取。
- `bootstrap` 负责把 shared config 映射为 application options，并装配具体适配器。
- `cmd/risk-server` 是组合根和进程入口，不承载业务逻辑。

- 当前 Swagger 注释和 HTTP response doc 应尽量保留，避免文档生成结果大幅波动。

## 5. 领域模型规划

### 5.1 基础枚举和值对象

建议领域层定义服务内部稳定模型，避免 application 直接使用 proto 枚举。

```go
type Scene string

const (
    SceneUnknown  Scene = "unknown"
    SceneLogin    Scene = "login"
    SceneRegister Scene = "register"
    ScenePayment  Scene = "payment"
)

type Action string

const (
    ActionPass   Action = "pass"
    ActionVerify Action = "verify"
    ActionReject Action = "reject"
)

type BlacklistType string

const (
    BlacklistTypeIP     BlacklistType = "ip"
    BlacklistTypeUserID BlacklistType = "uid"
)
```

### 5.2 风控检测模型

```go
type CheckCommand struct {
    ReqID        string
    Scene        Scene
    IP           string
    UserID       string
    PhoneNumber  string
    DeviceID     string
    Timestamp    int64
}

type CheckDecision struct {
    Action Action
    Reason string
}
```

### 5.3 事件上报模型

```go
type ReportEventCommand struct {
    ReqID      string
    Scene      Scene
    IP         string
    UserID     string
    IsSuccess  bool
    ExtraInfo  string
}

type ReportEventResult struct {
    Received bool
}
```

### 5.4 黑名单模型

```go
type AddBlacklistCommand struct {
    Type     BlacklistType
    Value    string
    Reason   string
    ExpireAt int64
}

type BlacklistEntry struct {
    Type     BlacklistType
    Value    string
    Reason   string
    ExpireAt int64
}
```

### 5.5 风险 IP 洞察模型

当前 `RiskIPSummary`、`RiskIPDetail`、`RiskIPEvent`、列表响应和事件列表响应可以迁入 domain 或 application。

建议：

- 聚合实体和值对象放 `domain`。
- 分页查询对象和 use case response 放 `application`。
- HTTP 文档模型继续放 inbound HTTP adapter。

## 6. 端口设计

### 6.1 入站端口

路径：

```text
internal/risk/application/ports/inbound.go
```

建议接口：

```go
type RiskCheckUseCase interface {
    Check(ctx context.Context, cmd application.CheckCommand) (application.CheckDecision, error)
}

type RiskEventUseCase interface {
    ReportEvent(ctx context.Context, cmd application.ReportEventCommand) (application.ReportEventResult, error)
}

type BlacklistUseCase interface {
    AddBlacklist(ctx context.Context, cmd application.AddBlacklistCommand) (application.AddBlacklistResult, error)
}

type UserThrottleUseCase interface {
    OnlineSelfTest(ctx context.Context, cmd application.UserActionCommand) (application.UserActionResult, error)
    JudgeSubmission(ctx context.Context, cmd application.UserActionCommand) (application.UserActionResult, error)
}

type RiskInsightQuery interface {
    ListRiskIPs(ctx context.Context, query application.RiskIPListQuery) (application.RiskIPListResponse, error)
    GetRiskIP(ctx context.Context, ip string) (application.RiskIPDetail, error)
    ListRiskIPEvents(ctx context.Context, ip string, query application.RiskIPEventsQuery) (application.RiskIPEventsResponse, error)
}
```

实际实现时可以把前四个接口由同一个 `RiskUseCase` 实现，也可以按文件拆分实现。接口按调用方视角拆开，方便 HTTP/gRPC handler 只依赖自己需要的能力。

### 6.2 出站端口

路径：

```text
internal/risk/application/ports/outbound.go
```

建议接口：

```go
type BlacklistRepository interface {
    Get(ctx context.Context, entryType domain.BlacklistType, value string) (domain.BlacklistEntry, bool, error)
    Save(ctx context.Context, entry domain.BlacklistEntry) error
}

type RateLimiter interface {
    IncrementAndCheck(ctx context.Context, key domain.RateLimitKey, rule domain.RateLimitRule) (domain.RateLimitResult, error)
}

type LoginFailureCounter interface {
    GetByIP(ctx context.Context, ip string) (int64, error)
    GetByUserID(ctx context.Context, userID string) (int64, error)
    RecordFailure(ctx context.Context, target domain.LoginFailureTarget, ttlSeconds int) (int64, error)
    Clear(ctx context.Context, target domain.LoginFailureTarget) error
}

type RiskInsightRepository interface {
    RecordCheck(ctx context.Context, event domain.RiskCheckInsight) error
    RecordReportEvent(ctx context.Context, event domain.RiskReportInsight) error
    RecordBlacklist(ctx context.Context, event domain.RiskBlacklistInsight) error
    ListIPs(ctx context.Context, query application.RiskIPListQuery) (application.RiskIPListResponse, error)
    GetIP(ctx context.Context, ip string) (domain.RiskIPDetail, error)
    ListIPEvents(ctx context.Context, ip string, query application.RiskIPEventsQuery) (application.RiskIPEventsResponse, error)
}
```

注意：

- Redis key 设计不要泄漏到 application。
- Lua 脚本只允许存在于 Redis adapter。
- `redis.Nil` 不应穿透到 application，统一转换为 `found=false` 或领域错误。
- application 层只关心“是否命中、当前计数、是否超过阈值、查询结果”。

## 7. 错误模型

建议在 `domain/errors.go` 或 `application/errors.go` 中定义稳定错误：

```go
var (
    ErrInvalidRequest       = errors.New("invalid risk request")
    ErrInvalidIP            = errors.New("invalid risk ip")
    ErrRiskIPNotFound       = errors.New("risk ip not found")
    ErrUnsupportedScene     = errors.New("unsupported scene")
    ErrIdentityEmpty        = errors.New("identity empty")
    ErrUserIDEmpty          = errors.New("user id empty")
    ErrRateLimitExceeded    = errors.New("rate limit exceeded")
    ErrInvalidBlacklistType = errors.New("invalid blacklist type")
)
```

错误映射规则：

- gRPC adapter 将应用错误映射为 `codes.InvalidArgument`、`codes.NotFound`、`codes.ResourceExhausted` 等。
- HTTP adapter 将应用错误映射为 `400`、`404`、`429` 或 `500`。
- application 不再直接返回 `status.Error`。
- application 不再直接拼接 HTTP error code。

## 8. 配置映射

当前业务层直接依赖：

```text
internal/shared/config.RiskRulesConfig
```

重构后建议在 application 层定义自己的 options：

```go
type RiskOptions struct {
    Login         LoginOptions
    IPRateLimit   RateLimitOptions
    UserRateLimit UserRateLimitOptions
}
```

在 `internal/risk/bootstrap/config_mapper.go` 中完成映射：

```go
func RiskOptionsFromSharedConfig(cfg *config.RiskRulesConfig) application.RiskOptions
```

原则：

- shared config 只在 `cmd` 和 `bootstrap` 出现。
- application options 使用业务语义命名。
- options 在构造 use case 时完成默认值和基本合法性校验。

## 9. 分阶段实施计划

### 阶段 0：建立重构保护网

目标：在不改变代码结构前，先把当前行为固定下来。

建议任务：

1. 为 `internal/risk/service/risk.go` 当前行为补单元测试或集成式 fake Redis 测试。
2. 覆盖 `Check`：
   - nil request。
   - IP 为空。
   - IP 黑名单命中。
   - 用户黑名单命中。
   - IP 限流触发。
   - 登录失败次数达到阈值。
   - 正常通过。
3. 覆盖 `ReportEvent`：
   - nil request。
   - 非登录场景。
   - userID 和 IP 都为空。
   - 登录成功清除计数。
   - 登录失败累加计数。
4. 覆盖 `AddBlacklist`：
   - IP 黑名单。
   - 用户黑名单。
   - 过期时间已过。
5. 覆盖 `OnlineSelfTest` / `JudgeSubmission`：
   - userID 为空。
   - 频控通过。
   - 频控触发。
6. 覆盖 HTTP admin handler 已有行为，保证错误码不变。
7. 为风险 IP 查询补最小测试，至少覆盖分页、非法 IP、不存在 IP。

验收标准：

- `go test ./...` 通过。
- 新增测试能反映现有外部行为。
- 不改 HTTP 路径、gRPC proto、Redis key。

### 阶段 1：创建 domain 与 application ports

目标：先建立新的架构骨架，不迁移业务。

建议任务：

1. 新增 `internal/risk/domain`。
2. 新增 `internal/risk/application`。
3. 新增 `internal/risk/application/ports`。
4. 定义领域枚举、命令、结果、错误。
5. 定义入站端口和出站端口。
6. 暂不接入入口，避免一次性大改。

验收标准：

- 新包能独立编译。
- `domain` 不依赖外部框架。
- `application/ports` 不依赖 Redis、Gin、gRPC、proto。

### 阶段 2：迁移风控检测用例

目标：把 `Check` 的业务编排迁到 application。

建议任务：

1. 新增 `application/check_usecase.go`。
2. 将黑名单检测、IP 限流、登录失败次数判断迁入 use case。
3. use case 通过 `BlacklistRepository`、`RateLimiter`、`LoginFailureCounter`、`RiskInsightRepository` 访问外部能力。
4. 用 fake port 写 application 单元测试。
5. 保持旧 `RiskService.Check` 对外签名不变，内部临时委托给新 use case。

验收标准：

- `RiskService.Check` 行为不变。
- `application` 测试不需要真实 Redis。
- `go test ./...` 通过。

### 阶段 3：迁移事件上报与登录失败计数

目标：把 `ReportEvent` 的业务编排迁到 application。

建议任务：

1. 新增 `application/event_usecase.go`。
2. 将登录场景校验、身份解析、成功清除、失败累加迁入 use case。
3. 将当前 insight 计数行为通过 `RiskInsightRepository` 抽象出去。
4. 旧 `RiskService.ReportEvent` 临时委托给新 use case。

验收标准：

- 登录成功/失败的 Redis key 行为不变。
- 事件上报错误码由旧 service adapter 保持一致。
- 用例测试覆盖成功和失败路径。

### 阶段 4：迁移黑名单和用户限流用例

目标：把 `AddBlacklist`、`OnlineSelfTest`、`JudgeSubmission` 迁到 application。

建议任务：

1. 新增 `application/blacklist_usecase.go`。
2. 新增 `application/throttle_usecase.go`。
3. 黑名单类型转换从 proto adapter 移走，application 只接收领域类型。
4. 用户行为限流统一复用 `RateLimiter`。
5. 旧 `RiskService` 对应方法临时委托新 use case。

验收标准：

- gRPC 响应和错误码保持不变。
- 用户限流 scope 仍为 `online_self_test` 和 `judge_submission`。
- 黑名单 Redis key 仍为 `risk:blacklist:ip:{ip}` 和 `risk:blacklist:uid:{userID}`。

### 阶段 5：拆分 Redis 出站适配器

目标：把 Redis key、Lua、序列化和查询从业务层移出。

建议任务：

1. 新增 `adapter/outbound/redis/keys.go`。
2. 新增 `adapter/outbound/redis/scripts.go`。
3. 拆出 `blacklist_repository.go`。
4. 拆出 `rate_limiter.go`。
5. 拆出 `login_failure_repository.go`。
6. 拆出 `insight_repository.go`。
7. 将 Redis adapter 实现 application outbound ports。
8. 保持所有 key 与当前一致：
   - `risk:blacklist:ip:{ip}`
   - `risk:blacklist:uid:{userID}`
   - `risk:rate:ip:{ip}`
   - `risk:rate:user:{userID}:{scope}`
   - `risk:fail_count:login:uid:{userID}`
   - `risk:fail_count:login:ip:{ip}`
   - `risk:insight:ip:index:last_seen`
   - `risk:insight:ip:profile:{ip}`
   - `risk:insight:ip:events:{ip}`
   - `risk:insight:ip:login_fail:{ip}`

验收标准：

- `internal/risk/application` 不 import Redis。
- Redis adapter 有针对 key、TTL、分页、Lua 的测试。
- 当前已有 Redis 数据无需迁移即可读取。

### 阶段 6：迁移风险 IP 后台查询

目标：把风险 IP 查询从旧 service 包迁到 application + Redis adapter。

建议任务：

1. 新增 `application/insight_query.go`。
2. 将 `RiskIPListQuery`、`RiskIPEventsQuery`、分页 response 迁入 application。
3. 将 `RiskIPSummary`、`RiskIPDetail`、`RiskIPEvent` 迁入 domain 或 application。
4. 将 IP 标准化、风险 flags、severity 计算放到 domain 或 application。
5. 将 Redis 读取细节留在 `insight_repository.go`。
6. HTTP admin handler 改为依赖 `ports.RiskInsightQuery`。

验收标准：

- HTTP admin API JSON 字段不变。
- 非法 IP、未找到、分页参数错误的 HTTP 状态码不变。
- `internal/risk/adapter/inbound/http` 不再 import `internal/risk/service`。

### 阶段 7：新增 gRPC 入站适配器

目标：让 gRPC server 实现从业务 service 中移出。

建议任务：

1. 新增 `adapter/inbound/grpc/risk_control_service.go`。
2. 在该 adapter 中 embed `pb.UnimplementedRiskControlServiceServer`。
3. adapter 持有 application 入站端口。
4. 新增 `mapper.go` 负责：
   - proto scene <-> domain scene。
   - proto action <-> domain action。
   - proto request -> application command。
   - application result -> proto response。
   - application error -> gRPC status error。
5. `cmd/risk-server` 注册新的 gRPC adapter，而不是旧 `RiskService`。

验收标准：

- `application` 不 import `risk-proto`。
- gRPC 方法、响应字段、错误码保持当前行为。
- `go test ./...` 通过。

### 阶段 8：HTTP 入站适配器目录迁移

目标：把当前 `transport` 迁入六边形 adapter 命名。

建议任务：

1. 新建 `internal/risk/adapter/inbound/http`。
2. 移动当前 `internal/risk/transport/*` 文件。
3. 包名可以继续使用 `http` 或 `httpadapter`，避免与标准库冲突时用 import alias。
4. 调整 import 路径。
5. 保留 Swagger 注释。
6. 保留 `NewHealthRouter` 兼容函数或同步修改入口调用。

验收标准：

- HTTP 路由保持不变。
- Swagger 注释仍能生成。
- `internal/risk/transport` 最终删除。

### 阶段 9：新增 bootstrap 组装层

目标：集中生产环境依赖装配，压缩 `cmd/risk-server/main.go`。

## 14. 主要风险与应对

### 14.1 Redis key 兼容风险

风险：key 格式、TTL 或列表顺序改变会影响线上数据和后台查询。

应对：

- 先把 key 常量集中到 Redis adapter。
- 用测试固定 key。
- 每次迁移只移动代码，不改 key。

### 14.2 gRPC 错误码变化风险

风险：application 错误重新映射时，调用方感知到错误码变化。

应对：

- 阶段 0 记录当前错误码。
- gRPC adapter 单独测试错误映射。
- application 不直接返回 gRPC status。

### 14.3 HTTP JSON 结构变化风险

风险：后台前端依赖现有字段名。

应对：

- 保留现有 JSON tag。
- HTTP adapter response doc 独立保留。
- 做 handler 级测试。

### 14.4 一次性移动文件过多导致回归困难

风险：目录迁移、业务迁移、适配器抽取混在一起，难定位问题。

应对：

- 先原地引入 application，再移动目录。
- 每阶段测试通过后再继续。
- 每个提交只做一个方向的变化。
