# Captcha 六边形架构说明

版本：`2026-05-03`

本文只说明 `captcha` 服务当前的六边形架构，目标是让后续维护者能快速判断：

- 代码应该放在哪一层；
- 请求从哪里进、从哪里出；
- 业务逻辑和基础设施之间的依赖方向是什么；
- 新增功能时应该遵守哪些边界。

## 一句话概括

`captcha` 服务现在以 `domain` 和 `application` 为核心，HTTP/gRPC 是入站适配器，Redis、go-captcha、外部图片源、图片池是出站适配器，生产环境组装集中在 `bootstrap` 和 `cmd/captcha-server`。

旧的 `internal/captcha/service` 包已经删除，不再作为兼容层或业务入口存在。

## 当前目录结构

```text
internal/captcha/
  domain/
    领域模型和领域错误

  application/
    应用用例、运行时图片源管理器、轨迹校验、生命周期逻辑

  application/ports/
    入站端口和出站端口接口

  adapter/inbound/
    http/
      HTTP handler、router、admin auth、Swagger 注释
    grpc/
      gRPC token 校验服务

  adapter/outbound/
    captcha/
      go-captcha 生成器适配器
    image/
      外部图片源 provider 和 fetcher
    imagepool/
      Redis 图片池、刷新调度、图片池端口适配器
    redis/
      Redis 仓储和运行时图片源配置存储

  bootstrap/
    生产环境组件组装、配置映射、启动恢复逻辑
```

服务入口在：

```text
cmd/captcha-server/main.go
```

## 依赖方向

核心规则：

```text
cmd/captcha-server
  -> bootstrap
  -> application ports + concrete adapters

adapter/inbound
  -> application/ports
  -> domain

application
  -> application/ports
  -> domain

adapter/outbound
  -> application/ports
  -> domain
```

`domain` 和 `application` 不能反向依赖外部技术细节。

当前边界要求：

- `domain` 不依赖 Redis、Gin、gRPC、go-captcha、shared config、net/http。
- `application` 不依赖 Redis、Gin、gRPC、go-captcha、shared config、net/http。
- `bootstrap` 可以依赖 shared config 和具体 adapter，因为它负责组装。
- `cmd/captcha-server` 是组合根，可以创建 Redis、logger、HTTP/gRPC server、Nacos registry。

可以用下面命令检查核心边界：

```bash
rg "internal/captcha/service|github.com/redis/go-redis|github.com/gin-gonic|google.golang.org/grpc|github.com/wenlng/go-captcha|internal/shared/config|net/http" internal/captcha/application internal/captcha/domain -n
```

期望结果：无输出。

## 各层职责

### domain

路径：

```text
internal/captcha/domain
```

职责：

- 定义验证码挑战、答案、轨迹点等领域模型；
- 定义图片池快照、图片元数据；
- 定义运行时图片源配置、patch、状态、校验结果；
- 定义领域错误，例如：
  - `ErrCaptchaNotFound`
  - `ErrImagePoolDisabled`
  - `ErrImagePoolRefreshInProgress`
  - `ImageSourceRefreshError`
  - `ImageSourcePersistenceError`

这一层只表达业务概念，不知道 Redis、HTTP、gRPC 或 go-captcha。

### application

路径：

```text
internal/captcha/application
```

职责：

- 编排验证码生成和校验；
- 编排 token 签发和校验；
- 编排运行时图片源查询、校验、更新、刷新；
- 管理图片池生命周期；
- 执行鼠标轨迹校验；
- 持有运行时图片源的内存状态。

主要文件：

| 文件 | 职责 |
| --- | --- |
| `captcha_usecase.go` | 生成/校验滑块验证码 |
| `token_usecase.go` | 签发/校验短期 token |
| `image_source_usecase.go` | 运行时图片源管理用例 |
| `runtime_image_source_manager.go` | 运行时图片源配置和 provider 的内存管理 |
| `lifecycle.go` | 图片池刷新生命周期 |
| `track_validator.go` | 鼠标轨迹校验 |

这一层通过端口访问外部能力，不直接操作 Redis 或 HTTP。

### application/ports

路径：

```text
internal/captcha/application/ports
```

职责：定义应用层需要的接口。

入站端口在 `inbound.go`：

- `CaptchaUseCase`
- `TokenUseCase`
- `ImageSourceUseCase`
- `CaptchaLifecycle`

出站端口在 `outbound.go`：

- `CaptchaAnswerRepository`
- `TokenRepository`
- `SliderGenerator`
- `BackgroundImagePool`
- `ManagedBackgroundImagePool`
- `ImageProvider`
- `ImageProviderFactory`
- `RuntimeImageSourceManager`
- `RuntimeImageSourceStore`

端口是六边形架构的关键：应用层只认识接口，不认识具体实现。

### adapter/inbound/http

路径：

```text
internal/captcha/adapter/inbound/http
```

职责：

- 接收 HTTP 请求；
- 解析 JSON；
- 调用应用层入站端口；
- 把领域/应用错误转换为 HTTP 响应；
- 管理 admin 接口鉴权；
- 提供 Swagger 注释和模型。

主要 handler：

| 文件 | 职责 |
| --- | --- |
| `captcha_handler.go` | 生成验证码、校验验证码并签发 token |
| `image_source_handler.go` | 运行时图片源管理接口 |
| `health_handler.go` | 健康检查 |
| `admin_auth.go` | admin header 鉴权 |
| `router.go` | 路由挂载 |

HTTP 管理接口路径：

```text
GET  /api/v1/admin/image-source
POST /api/v1/admin/image-source/validate
PUT  /api/v1/admin/image-source
POST /api/v1/admin/image-source/refresh
```

### adapter/inbound/grpc

路径：

```text
internal/captcha/adapter/inbound/grpc
```

职责：

- 实现 `risk-proto` 中的 captcha gRPC 服务；
- 当前主要提供 token 校验；
- 调用 `TokenUseCase`；
- 把应用结果转换为 proto response。

### adapter/outbound/redis

路径：

```text
internal/captcha/adapter/outbound/redis
```

职责：

- 保存/读取验证码答案；
- 保存/检查 token；
- 保存图片池图片数据和元数据；
- 保存/读取运行时图片源配置。

主要文件：

| 文件 | 职责 |
| --- | --- |
| `answer_repository.go` | 验证码答案仓储 |
| `token_repository.go` | token 仓储 |
| `image_pool_repository.go` | 图片池 Redis 存储 |
| `image_source_store.go` | 运行时图片源配置持久化 |

运行时图片源配置 Redis key：

```text
captcha:image-source:runtime-config
```

### adapter/outbound/captcha

路径：

```text
internal/captcha/adapter/outbound/captcha
```

职责：

- 封装 `go-captcha`；
- 根据背景图生成滑块验证码；
- 返回生成后的图片和答案。

应用层不直接依赖 `go-captcha`，只依赖 `SliderGenerator` 端口。

### adapter/outbound/image

路径：

```text
internal/captcha/adapter/outbound/image
```

职责：

- 构造外部图片 provider；
- 调用上游图片 API；
- 兼容直接图片、JSON URL、base64、data URI 等响应；
- 下载和规范化图片；
- 转换为图片池可使用的 `domain.ImageMeta`。

主要文件：

| 文件 | 职责 |
| --- | --- |
| `provider_factory.go` | 根据运行时配置构造 provider |
| `fetcher.go` | 外部图片拉取、解析、规范化 |

### adapter/outbound/imagepool

路径：

```text
internal/captcha/adapter/outbound/imagepool
```

职责：

- 维护 Redis 背景图片池；
- 控制刷新并发；
- 管理 active generation；
- 定时刷新；
- 暴露图片池端口给应用层。

主要文件：

| 文件 | 职责 |
| --- | --- |
| `pool.go` | Redis 图片池核心行为 |
| `refresher.go` | 图片池刷新逻辑 |
| `scheduler.go` | 定时刷新调度 |
| `port_adapter.go` | 把具体图片池适配成应用端口 |

### bootstrap

路径：

```text
internal/captcha/bootstrap
```

职责：

- 把 shared config 转换为 application/adapter options；
- 构造生产用 use case；
- 构造图片池；
- 构造 runtime image-source manager；
- 从 Redis 恢复运行时图片源配置；
- 给 `cmd/captcha-server` 提供清晰的组件创建函数。

主要入口：

| 函数 | 职责 |
| --- | --- |
| `NewCaptchaComponents` | 构造验证码 use case、图片池、生命周期 |
| `NewRuntimeImageSourceComponents` | 构造运行时图片源 manager/use case/store |
| `NewTokenUseCase` | 构造 token use case |
| `NewConfiguredImagePool` | 构造 Redis 图片池 |

## 主要请求链路

### 生成验证码

```text
GET /api/v1/captcha
  -> adapter/inbound/http.CaptchaHandler
  -> application.CaptchaUseCase.Generate
  -> outbound image pool 读取背景图
  -> outbound captcha generator 生成滑块验证码
  -> outbound Redis answer repository 保存答案
```

如果图片池未启用，生成器会走无背景图或默认逻辑，具体由应用用例和生成器适配器处理。

### 校验验证码并签发 token

```text
POST /api/v1/captcha/verify
  -> adapter/inbound/http.CaptchaHandler
  -> application.CaptchaUseCase.Verify
  -> track validator 校验鼠标轨迹
  -> outbound Redis answer repository 校验答案
  -> application.TokenUseCase.Issue
  -> outbound Redis token repository 保存 token digest
```

HTTP handler 不直接操作 Redis，也不直接生成 token。

### gRPC 校验 token

```text
gRPC CaptchaTokenService.VerifyToken
  -> adapter/inbound/grpc.CaptchaTokenService
  -> application.TokenUseCase.Verify
  -> outbound Redis token repository 检查 token digest
```

### 运行时更新图片源

```text
PUT /api/v1/admin/image-source
  -> adapter/inbound/http.ImageSourceAdminHandler
  -> application.ImageSourceUseCase.Update
  -> application.RuntimeImageSourceManager 构造候选配置
  -> outbound image provider factory 构造 provider
  -> provider 拉取 1 张图片做真实校验
  -> outbound Redis runtime image-source store 持久化配置
  -> manager 应用新配置和 provider
  -> outbound image pool 按需刷新
```

运行时图片源的内存状态在 `RuntimeImageSourceManager`，持久化状态在 Redis。

## 启动组装流程

`cmd/captcha-server/main.go` 的核心组装顺序：

1. 加载配置；
2. 初始化 logger；
3. 初始化 Redis；
4. 调用 `bootstrap.NewCaptchaComponents`；
5. 调用 `bootstrap.NewRuntimeImageSourceComponents`；
6. 调用 `bootstrap.NewTokenUseCase`；
7. 构造 HTTP handler；
8. 构造 gRPC handler；
9. 启动图片池刷新任务；
10. 启动 HTTP/gRPC server；
11. 注册 Nacos；
12. 接收退出信号并优雅关闭。

`cmd` 可以接触具体技术和 adapter；`application` 不可以。

## 运行时图片源的几个状态

运行时图片源涉及四个不同概念：

| 概念 | 类型/位置 | 说明 |
| --- | --- | --- |
| 启动配置 | `config.CaptchaConfigSpec.ExternalImageAPI` | 进程启动时的默认图片源 |
| 运行时配置 | `domain.ImageSourceRuntimeConfig` | 当前内存里生效的图片源配置 |
| 持久化配置 | Redis key `captcha:image-source:runtime-config` | 最近一次成功保存的运行时配置 |
| 当前 provider | `RuntimeImageSourceManager` 内部状态 | 图片池刷新时实际使用的图片来源 |

不要把这四个概念混成一个对象。

## 错误处理约定

运行时图片源相关错误在 `domain` 中定义：

- `ErrImagePoolDisabled`
- `ErrImagePoolRefreshInProgress`
- `ImageSourceRefreshError`
- `ImageSourcePersistenceError`

HTTP adapter 负责把这些错误映射为 HTTP 状态码和错误码：

- 图片池禁用：`409`
- 刷新进行中：`409`
- 刷新失败：`502`
- 持久化失败：`500`
- 配置校验失败：`400`

应用层只返回领域错误，不关心 HTTP 状态码。

## 新增功能应该放哪里

### 新增 HTTP 接口

放在：

```text
internal/captcha/adapter/inbound/http
```

如果需要新业务能力，先在 `application/ports/inbound.go` 或已有 use case 上定义行为，再由 HTTP handler 调用。

### 新增 gRPC 接口

放在：

```text
internal/captcha/adapter/inbound/grpc
```

不要把 gRPC request/response 类型传进 application/domain。

### 新增 Redis 读写

放在：

```text
internal/captcha/adapter/outbound/redis
```

应用层应通过 port 调用，不直接依赖 `redis.Client`。

### 新增外部服务调用

建议：

1. 在 `application/ports/outbound.go` 定义端口；
2. 在 `adapter/outbound/<name>` 实现；
3. 在 `bootstrap` 里接线；
4. application 只依赖端口。

### 新增业务规则

优先放在：

- `domain`：纯领域模型或领域错误；
- `application`：需要编排仓储、外部端口或多个领域对象的用例逻辑。

不要放在 HTTP handler 或 Redis adapter 里。

## 当前不应该做的事

- 不要重建 `internal/captcha/service`。
- 不要让 `application` 直接 import Redis/Gin/gRPC/shared config。
- 不要让 handler 直接操作 Redis。
- 不要把 config 结构一路传进业务核心。
- 不要在 adapter 里实现核心业务规则。
- 不要把 HTTP DTO 或 proto DTO 放进 domain。
